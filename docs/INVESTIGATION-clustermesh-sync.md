# Investigation: clustermesh etcd sync failure (full-Helm / option A)

Status: ROOT CAUSE FOUND (2026-09-27 ~05:30Z) — **H6: TLS hostname mismatch**.
Mesh wiring never converged because kvstoremesh's Go etcd client rejects the
remote etcd's server certificate: the cert SANs do not contain the NLB
hostname it dials. Fix = make the dialed name match the cert (see "Fix
options" below). Option B no longer needed to unblock.

## Goal of option A

Pure-IaC mesh: each cluster's helm values carry the remote cluster's
clustermesh-apiserver address; kvstoremesh connects to the peer's mesh etcd
and caches remote state locally; agents read it from there. No cilium CLI.

## ROOT CAUSE — H6: server cert SAN vs NLB hostname (CONFIRMED 05:30Z)

kvstoremesh dials `https://<NLB-hostname>:2379`. Go's TLS client verifies the
server cert against that hostname. The etcd serving cert (helm certgen) has:

```
SANs: DNS:clustermesh-apiserver.cilium.svc, DNS:*.mesh.cilium.io,
      IP:127.0.0.1, IP:::1
```

NLB hostname (`k8s-cilium-clusterm-...elb.ap-south-1.amazonaws.com`) is NOT in
SANs → client aborts the handshake with alert `bad certificate` → etcd logs
`remote error: tls: bad certificate` → watcher list/heartbeat RPCs never
complete → 15s readiness timeout → "context canceled" → 15-min retry loop.

Empirical proof (probe pod in cluster-2, secret
`clustermesh-apiserver-remote-cert`):
- `s_client -CAfile ca.crt` (no hostname check): **Verification: OK**, TLS1.3,
  mutual auth with client cert works fine.
- same + `-verify_hostname <NLB-hostname>`: **Verify return code: 62
  (hostname mismatch)**.

### Why earlier hypotheses are dead
- **H1 MTU blackhole: DEAD.** DF pings pod→remote node at 1400/1450/2000/8000B
  all pass; pod eth0 mtu 9001 (no overlay on etcd path).
- **H3 stale mounts: DEAD.** kvm pod (re)started after cert regen; its mounted
  files come from the same `clustermesh-apiserver-remote-cert` secret the
  successful probe used.
- **Signature #3 "handshake hangs WITH client cert": ARTIFACT.** The probe
  configMap `tls-certs` had an EMPTY `c.key` → openssl errored/prompted
  silently. With the real secret the handshake completes instantly.
- **H2 etcd auth: untested but moot** — TLS dies before auth is reached. Once
  SAN fix lands, if RPC-layer auth errors appear, revisit (users `remote` vs
  `remote-cluster-2`).
- **H4 (10.2.0.162 client): still unidentified** — a cluster-1 pod IP
  (10.2.0.0/16 = cluster-1 pod CIDR) hitting cluster-1's own NLB with a client
  cert, same `bad certificate` alert. No current pod/cep owns that IP. Same
  failure class; re-check after fix.

## Fix options (option A preserved, pure IaC)

### Fix 1 (recommended): dial a name the cert already covers — `*.mesh.cilium.io`
certgen already ships `*.mesh.cilium.io` in the server cert SANs — this SAN
exists precisely for pointing a stable DNS name at the apiserver LB.
- Route53 **private hosted zone `mesh.cilium.io`**, associated to BOTH VPCs.
- `cluster-1.mesh.cilium.io` CNAME → cluster-1 NLB hostname;
  `cluster-2.mesh.cilium.io` CNAME → cluster-2 NLB hostname.
- helm: `clustermesh.config.clusters.<peer>.address = cluster-N.mesh.cilium.io`
  (hostname only, port stays 2379).
- No cert regeneration, no apiserver cert churn — only the kvstoremesh config
  secret changes → restart clustermesh-apiserver pods.
- terraform: new `aws_route53_zone` + `aws_route53_record`s + vpc associations;
  hostnames already known (same remote-state outputs used today).

### Fix 2: add NLB name to the cert — `extraDnsNames`
- helm value `clustermesh.apiserver.tls.server.extraDnsNames` with either the
  exact NLB hostname (two-pass: NLB must exist before certs render → ordering
  cycle in terraform) or wildcard `*.elb.ap-south-1.amazonaws.com` (single
  label, matches; but = minting a cert for an amazon-owned domain).
- Cost: server cert regen + apiserver restart on both clusters.

### Fix 3: disable hostname verification in the etcd client
- Not exposed by cilium's kvstore etcd config. Dead.

## The failure signatures

**1. kvstoremesh (cluster-2 → cluster-1's NLB) — loops every ~15s:**
```
Creating etcd client ... configPath=/var/lib/cilium/clustermesh/cluster-1
Connecting to etcd server... endpoints=[https://k8s-cilium-clusterm-22197d4995-...:2379]
Starting watcher ...
Unable to list keys before starting watcher, will retry
    error="context canceled" prefix=cilium/.heartbeat attempt=0
Remote cluster did not connect within timeout, removing from readiness checks
    (15s after watcher start — the leader-lifecycle readiness timeout)
timed out while starting the heartbeat     (etcd client session heartbeat)
```
Both a READ (list keys, prefix `cilium/.heartbeat`) and a WRITE (heartbeat)
never complete — the etcd client RPC stalls, then the KVM 15s readiness
timeout cancels the context ("context canceled" = self-inflicted cancel).

**2. cluster-1's etcd — rejects incoming client TLS connections:**
```
rejected connection on client endpoint
  remote-addr: 10.1.10.80  (cluster-2 node — kvstoremesh SNATed)
  remote-addr: 10.2.0.162  (cluster-1's cilium Envoy proxy IP!)
  error: "remote error: tls: bad certificate"
```
`remote error:` = the alert came FROM THE CLIENT — i.e. the client received
the server's certificate, REJECTED it, and sent `bad certificate` back.

**3. Manual repro from a cluster-1 pod → local mesh etcd VIP**
(`clustermesh-apiserver.cilium.svc:2379`) WITH the client cert
(`clustermesh-apiserver-remote-cert`): the TLS handshake HANGS — zero
output from s_client for minutes. WITHOUT the client cert: handshake
completes, server chain presented, issuer = shared CA (verify fails only
because no CAfile passed).

**4. Agents:** `Connection to remote cluster established` (to the LOCAL
kvstoremesh etcd — etcdClusterID matches the remote) then
`Unable to get remote cluster configuration: not found` every 3 min.
`cilium status` = `0/1 remote clusters ready`, status json: `synced: {}`,
`leases=0` — kvstoremesh has written NOTHING into the local mesh etcd.

## Working hypotheses (ranked)

### H1 — MTU blackhole on the cert-flight packets (most likely)
The TLS handshake HANGS exactly when the client cert is included (probe
with cert = hang; probe without = completes). The client cert flight =
~1.5-2 KB = multi-segment. If one segment size is dropped on the path
(client→etcd or etcd→client), the handshake stalls silently — matches BOTH
the hangs and the "list/heartbeat timeout" (etcd RPCs = small handshake +
larger payloads later).

Test:
```bash
# from a cluster-2 pod, DF-ping cluster-1's node IP at increasing sizes
ping -M do -s 1400 10.0.11.241
ping -M do -s 2000 10.0.11.241   # expect fail if MTU issue on the pod path
# also test from host network vs pod network — isolates overlay vs VPC leg
```
Check cilium MTU config: pods run cilium overlay (VXLAN+WG) → pod MTU
~1450; the etcd path = pod → SNAT → VPC (MTU 9001). A pod-originated
1.4KB packet fits — but WG'd node-to-node segments of the SAME flow... the
etcd path should NOT traverse WG (NLB ≠ cilium node). If pings confirm
size-dependent drops → tune cilium MTU / test with smaller cert chain.

### H2 — the etcd rejects CN=remote because user `remote` doesn't exist
authMode=migration: etcd user store has `remote-cluster-2` (role `remote`).
The kvstoremesh presents `clustermesh-apiserver-remote-cert` with subject
**CN=remote**. etcd maps cert CN → username. If user `remote` was never
provisioned (only `remote-cluster-2` was), authz fails. etcd SHOULD error
"user not found" at RPC layer (not a TLS alert) — but etcd's TLS+auth
interaction may surface as a TLS-layer reject first.

Test:
```bash
# in cluster-1's etcd (no shell — use the etcd container's env or a debug pod)
ETCDCTL_API=3 etcdctl --endpoints=localhost:2379 \
  --cacert=/var/lib/etcd-secrets/ca.crt \
  --cert=/var/lib/cilium/etcd/etcd-client.crt \
  --key=/var/lib/cilium/etcd/etcd-client.key auth status
ETCDCTL_API=3 etcdctl ... user list
ETCDCTL_API=3 etcdctl ... role list
# expect: users remote + remote-cluster-2, role remote
```
If `remote` user is missing → switch authMode to `cluster` (CN=remote-
cluster-2 matches the provisioned user) in both stacks and re-apply.

### H3 — cert visibility asymmetry (stale mounts)
All secrets verified correct AT THE API LEVEL. But containers mount
PROJECTED volumes — if any pod started BETWEEN the secret delete and the
helm certgen re-creating them, kubelet may have pinned the OLD (deleted)
cert content until the next projected-volume sync (~1 min) — and the
running processes keep the OLD in-memory TLS state until restarted.

The etcd rejects came from BOTH a fresh etcd pod AND the fresh
kvstoremesh — but their mounts were refreshed at different seconds. A
single clean restart of BOTH clustermesh-apiserver deployments (done) may
not have been enough if the secret regeneration landed between the two
restarts.

Test: one more `rollout restart deploy/clustermesh-apiserver` on both
clusters NOW (certs are stable since 04:18Z), then watch kvstoremesh logs.

### H4 — the Envoy-proxy connection path
`10.2.0.162` = cluster-1's cilium Envoy proxy IP — an etcd client connection
arriving FROM Envoy = some pod's traffic is being transparently proxied.
Identify it:
```bash
kubectl --context cluster-1 -n cilium get po -o wide | grep 10.2.0.162
hubble observe --context cluster-1 --from 10.2.0.162 --to 10.2.x.x:2379
```
If the rejected connections = cilium's own envoy L7 steering something
unexpectedly, that's a datapath red herring — but worth ruling out.

### H5 — helm certgen vs terraform ordering races (already partially fixed)
Original bugs (fixed, but contributed to the churn):
- `clustermesh.config.clusters.<name>.address` must be the HOSTNAME ONLY —
  the chart template appends `:{{ $cluster.port }}` itself; my
  `<host>:2379` + unset `port` rendered `:<no value>` into the etcd config.
  Fixed: address = hostname + separate `port` set entry.
- The shared CA must be `cilium-ca` (cilium ns, keys `ca.crt`/`ca.key`) —
  now provided via helm VALUES (`tls.ca.cert`/`tls.ca.key`, base64) which
  the chart prefers (`cilium.ca.setup` → `buildCustomCert`), eliminating
  the secret/ordering race entirely.

## Why option B sidesteps the problem

`cilium clustermesh connect` does not push remote etcd addresses through
helm-rendered etcd configs. It: extracts each cluster's CA, generates and
DISTRIBUTES per-cluster client certs, writes the clustermesh config secrets
itself, and validates the full handshake path before declaring success —
the same etcd-over-NLB path, but with cilium-CLI-managed certs that are
known to work with authMode's expectations.
